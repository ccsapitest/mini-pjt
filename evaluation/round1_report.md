## 핵심 교훈: 오늘 "회귀"로 보였던 문제 대부분은 평가 스크립트 버그였다

이전 재실행들에서 관찰됐던 두 가지 심각해 보이던 문제—**(H) 같은 도구 호출을 통째로 2~3번
반복**, **(I) `update_user_preference` 관련 `ValidationException`**—는 에이전트 코드가 아니라
`run_eval.py`가 **매번 같은 thread_id(`eval_1`~`eval_18`)를 쓰면서 `checkpoints.sqlite`를 지우지
않았던 것**이 원인이었다. 그 결과:
- 도구 호출 횟수(`ToolCallLimitMiddleware`)가 스레드별로 실행할 때마다 누적되어, 여러 번
  재평가를 돌릴수록 한도(25)에 더 빨리 도달했다.
- 11·16·17번 스레드는 예전 실행에서 한 번 깨졌던 상태가 그대로 저장되어 있어서, 모델을
  Sonnet에서 Haiku로 바꿔도 **완전히 동일한 tool_use id로 동일한 에러가 재현**됐다 (실시간
  버그가 아니라 저장된 상태 replay라는 결정적 증거).

`run_eval.py`에 `_reset_checkpoints()`를 추가해 실행 시작 시 `checkpoints.sqlite`를 항상 지우도록
고친 뒤 재실행하니, H·I 둘 다 완전히 사라지고 18/18 통과했다. 이 과정에서 부수적으로 오늘 있었던
"E 일관성 없음(16번 실패)" 문제도 사실은 이 스크립트 버그의 영향이었을 가능성이 높다는 게
확인됐다.

**교훈**: 상태를 저장하는(체크포인터가 있는) 에이전트를 반복 평가할 때는, 평가 스크립트가
매 실행마다 상태를 완전히 초기화하는지 반드시 확인해야 한다. 그렇지 않으면 에이전트 자체의
문제와 평가 인프라의 문제를 구분할 수 없다.
