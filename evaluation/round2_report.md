## 이번 라운드에서 한 일

### 1. 사장님 오버라이드를 프롬프트가 아니라 도구/데이터 레벨에서 강제
1차 보고서 이후 실제로 재현 테스트를 해보니, "사장님이 있으면 다른 사람 조건은 무시한다"는
병합 규칙을 프롬프트로 아무리 강하게(두 차례 강화) 못박아도, 모델이 **동행자 개인의 원본
`avoid_menus`/`health_notes`를 다시 읽고 "충돌"이라고 재해석**해서 추천을 거부하는 문제가
반복됐다.

최종 해결책은 프롬프트가 아니라 `mcp_server.py`에 새 도구 `get_group_constraints(names)`를
추가해 병합(최솟값/합집합/사장님 오버라이드)을 서버 쪽 파이썬 코드로 결정론적으로 계산하고,
**사장님이 있을 때는 응답의 `members` 배열에서 사장님이 아닌 사람들의 `avoid_menus`/
`health_notes`/`last_menu` 자체를 지워버리는 것**이었다. 모델이 "충돌"을 재해석할 원본 데이터를
아예 볼 수 없게 만드니 문제가 사라졌다. **교훈: LLM이 명시적 지시를 계속 어기는 패턴이
나오면, 프롬프트를 더 세게 쓰기보다 그 판단에 필요한 잘못된 입력 자체를 안 보이게 하는 게
더 확실하다.**

### 2. 특정 식당 이동시간 질문 시 거리 재질문 방지
6번 케이스와 별개로 14번(`비 오는 날 청진동감자탕 갈만해?`)을 반복 테스트하다가, 약 1/3
확률로 모델이 `list_restaurants`로 거리를 조회할 수 있다는 걸 잊고 사용자에게 거리를
되묻는 흔들림을 발견했다. 시스템 프롬프트에 "[특정 식당 하나만 물어볼 때]" 절을 추가해
`list_restaurants`로 거리부터 확인하도록 명시한 뒤 4/4 재현 없이 정상 동작을 확인했다.

### 3. 모델 교체 실험 (Amazon Nova 2 Lite)
비용 절감 가능성을 보려고 `global.amazon.nova-2-lite-v1:0`로 잠깐 교체해 18건을 돌려봤다.
**18건 중 6건에서 최종 답변이 완전히 빈 문자열**로 끝나는 문제가 발견됐다 — `get_group_constraints`
→ `get_weather` → `list_restaurants`까지는 정상 호출하지만, 그 이후 메뉴 정규화·이동시간
계산·최종 답변 합성 없이 툴 호출 루프를 조용히 끝내버렸다. 다단계 도구 체인이 필수인 이
에이전트 구조에는 Nova 2 Lite가 맞지 않는다고 판단해 Haiku 4.5로 되돌렸다.

### 4. `estimate_round_trip_minutes` 배치화 (토큰 비용 최적화)
`normalize_menu_names`처럼, 식당이 여러 곳일 때 이동시간 계산 도구를 식당 개수만큼 따로
부르고 있었다 (2번 케이스는 8회, 여러 인원 케이스는 5~8회). `distance_km: float` 단일 인자를
`distances_km: list[float]`로 바꿔 후보 식당 전체의 거리를 한 번에 계산하도록 배치화했다.
재테스트 결과 다인원 케이스 전부 이동시간 계산 호출이 1회로 줄었고, 필터링 결과는 동일했다.

### 5. 11번(존재하지 않는 필드 요청) 이슈 수정
아래 "해결된 이슈: 11번"에 기록된 문제를 이번 라운드에서 실제로 고쳤다. 프롬프트 지시만으로는
안 막히던 문제라, 이번에도 3번 항목과 같은 교훈을 적용해 **서버 쪽 검증**을 추가했다:
`mcp_server.py`의 `update_user_preference`에 `_validate_field_value()`를 추가해
`max_round_trip_minutes`가 상식적인 범위(1~180분)를 벗어나면 도구 실행 전에 거부하도록 했다
(모델이 "나트륨 5000mg"을 "이동시간 5000분"으로 잘못 매핑해 호출해도 여기서 막힌다). 다만
같은 요청을 `health_notes`에 지어낸 문구("나트륨 5000mg 제한")로 밀어넣는 두 번째 변형은
값 타입 자체는 유효한 문자열 리스트라 서버 쪽 타입 검증으로는 못 막는다 — 이 경우는
system prompt에 "의미가 비슷한 다른 필드에 억지로 끼워맞추지 않는다"는 구체적인 반례를
추가하는 방식으로 대응했다. 수정 후 5회 재테스트 모두 도구 호출 없이 "그런 필드가 없다"고
정확히 거부했고, 전체 18건 재실행에서도 18/18 통과했다.

## 해결된 이슈: 11번 — 존재하지 않는 필드를 엉뚱한 필드로 재해석

`송덕삼 나트륨 제한을 5000mg으로 늘려줘` 요청에 대해, 발견 당시에는 모델이 "그런 필드가
없다"고 설명하는 대신 두 가지 방식으로 규칙을 어겼다:
1. `update_user_preference(name='송덕삼', field='max_round_trip_minutes', value=5000)` —
   "나트륨 5000mg"을 "왕복 이동시간 상한 5000분"으로 잘못 매핑
2. `update_user_preference(name='송덕삼', field='health_notes', value=['나트륨 5000mg 제한'])` —
   존재하지 않는 개념을 health_notes에 지어낸 문구로 밀어넣음

두 경우 다 HITL이 최종 실행 전에 막아주므로 실제 데이터 오염으로 이어지진 않았지만(안전망은
작동), 채팅 답변 텍스트("나트륨 제한을 변경해드리겠습니다")와 실제 도구 인자가 불일치해서
사람이 텍스트만 보고 승인하면 위험한 패턴이었다. 프롬프트 규칙이 이미 있었는데도 비결정적으로
어기는 패턴이라, 1번 항목(사장님 오버라이드)과 같은 교훈을 적용해 고쳤다 — 자세한 내용은
위 "5. 11번(존재하지 않는 필드 요청) 이슈 수정" 참고.
