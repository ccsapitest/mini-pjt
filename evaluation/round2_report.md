## 이번 라운드에서 한 일

### 1. 사장님 오버라이드를 프롬프트가 아니라 도구/데이터 레벨에서 강제
1차 보고서 이후 실제로 재현 테스트를 해보니, "사장님이 있으면 다른 사람 조건은 무시한다"는
병합 규칙을 프롬프트로 아무리 강하게(두 차례 강화) 못박아도, 모델이 **동행자 개인의 원본
`avoid_menus`/`health_notes`를 다시 읽고 "충돌"이라고 재해석**해서 추천을 거부하는 문제가
반복됐다.

최종 해결책은 프롬프트가 아니라 `mcp_server.py`에 새 도구 `get_group_constraints(names)`를
추가해 병합(최솟값/합집합/사장님 오버라이드)을 서버 쪽 파이썬 코드로 결정론적으로 계산하고,
**사장님이 있을 때는 응답의 `members` 배열에서 사장님이 아닌 사람들의 `avoid_menus`/
`health_notes`/`last_menu` 자체를 지워버리는 것**이었다. 모델이 "충돌"을 재해석할 원본 데이터를
아예 볼 수 없게 만드니 문제가 사라졌다. **교훈: LLM이 명시적 지시를 계속 어기는 패턴이
나오면, 프롬프트를 더 세게 쓰기보다 그 판단에 필요한 잘못된 입력 자체를 안 보이게 하는 게
더 확실하다.**

### 2. 특정 식당 이동시간 질문 시 거리 재질문 방지
6번 케이스와 별개로 14번(`비 오는 날 청진동감자탕 갈만해?`)을 반복 테스트하다가, 약 1/3
확률로 모델이 `list_restaurants`로 거리를 조회할 수 있다는 걸 잊고 사용자에게 거리를
되묻는 흔들림을 발견했다. 시스템 프롬프트에 "[특정 식당 하나만 물어볼 때]" 절을 추가해
`list_restaurants`로 거리부터 확인하도록 명시한 뒤 4/4 재현 없이 정상 동작을 확인했다.

### 3. 모델 교체 실험 (Amazon Nova 2 Lite)
비용 절감 가능성을 보려고 `global.amazon.nova-2-lite-v1:0`로 잠깐 교체해 18건을 돌려봤다.
**18건 중 6건에서 최종 답변이 완전히 빈 문자열**로 끝나는 문제가 발견됐다 — `get_group_constraints`
→ `get_weather` → `list_restaurants`까지는 정상 호출하지만, 그 이후 메뉴 정규화·이동시간
계산·최종 답변 합성 없이 툴 호출 루프를 조용히 끝내버렸다. 다단계 도구 체인이 필수인 이
에이전트 구조에는 Nova 2 Lite가 맞지 않는다고 판단해 Haiku 4.5로 되돌렸다.

## 발견된 이슈: 11번 — 존재하지 않는 필드를 엉뚱한 필드로 재해석

`송덕삼 나트륨 제한을 5000mg으로 늘려줘` 요청에 대해, 이번 실행에서는 모델이 "그런 필드가
없다"고 설명하는 대신 `update_user_preference(name='송덕삼', field='max_round_trip_minutes',
value=5000)`를 호출했다. 즉 "나트륨 5000mg"을 엉뚱하게 "왕복 이동시간 상한 5000분"으로
재해석해 HITL 승인 대기에 올렸다. 채팅 답변 텍스트는 "나트륨 제한을 5000mg으로
변경해드리겠습니다"라고만 나오고, 실제로 무엇을 바꾸려는지(`max_round_trip_minutes`)는 HITL
승인 화면의 도구 인자를 봐야 알 수 있다.

- HITL이 최종 실행 전에 막아주므로 실제 데이터 오염으로 이어지지는 않았다 (안전망은 작동).
- 다만 답변 텍스트와 실제 도구 인자가 불일치하는 것은, 사람이 답변 텍스트만 보고 승인하면
  위험할 수 있는 패턴이다.
- 1차 라운드 및 이번 라운드의 다른 실행에서는 "그런 필드가 없다"고 정확히 거부한 적도 있어
  (프롬프트에 이미 규칙이 명시돼 있음에도) 비결정적으로 발생하는 것으로 보인다.

**다음 라운드 과제**: 재현 빈도를 좀 더 확인하고, 필요하면 "답변에서 언급하는 필드명과
실제 호출하는 field 인자가 다르면 호출하지 않는다"는 규칙을 프롬프트에 추가하거나, 애초에
`update_user_preference`의 `field`가 유효한 5개 중 하나가 아니면 서버 쪽(`mcp_server.py`)에서
거부하도록 방어하는 방안을 검토한다.
